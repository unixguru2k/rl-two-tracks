Most "learn RL" content sends app engineers down the wrong path.

It opens with CartPole. It ends with RLHF.
And somewhere in the middle, a backend engineer who just wants to pick the better response style for each user gives up — because none of it maps to the code they actually ship.

Two completely different jobs, one confused curriculum

Track B

Decision Optimization in Systems

Which action should my system take, given the current context, right now?

B0 Random Baseline — Establish the floor (control, not warm-up) ⭐
B1 Epsilon-Greedy Bandit — Best global default, no context ⭐
B2 Contextual Bandit (LinUCB) — Personalize with context ⭐⭐
B3 Q-Learning (Tabular) — Sequential decisions, small state space ⭐⭐
B4 Feature-Based Q-Learning — Large/continuous state space ⭐⭐⭐
B5 DQN — Raw high-dimensional state, neural network ⭐⭐⭐⭐
B6 Production Online Systems — Shipping to real users ⭐⭐⭐

No GPU, no reward model, no preference data. Just a measurable outcome and a key-value store.

The Most Common Mistake

This single question routes you to half the curriculum:

Do the ORDER of your decisions matter?

Does yesterday's decision change today's options?
NO → Bandits
Each decision is independent.
"Pick the best option RIGHT NOW."
B0, B1, B2
YES → MDP
Decisions are sequential.
"What leads to the BEST FUTURE?"
B3, B4, B5

Using a bandit for a sequential problem, or an MDP for an independent one, is the mistake this repo exists to prevent.

The Cross-Track Bridge

The most useful idea in this repo — the one point where the two tracks couple.

Track A — Produces JUDGES
Reward models · Preference models · Verifiers
RLHF'd models that can score outputs
→
Track B — Consumes JUDGES
Scores each served action
"Was this empathetic?" becomes a reward signal 
Without the bridge:
  serve response → ??? no measurable outcome → can't learn

With the bridge:
  serve response → Track A judge scores it 0..1 → Track B bandit updates

This is the answer to "how do I do RL on things I can't measure with a click."
It is not RLHF on your own model — it is using someone else's RLHF'd model as a measuring instrument.

The 2026 Post-Training Stack

If you were building from scratch today, the canonical order:

STEP 1
SFT
Supervised fine-tune on demonstrations
→
STEP 2
Light Preference
DPO / SimPO / ORPO / KTO
→
STEP 3
RLVR — if needed
GRPO / DAPO / GSPO
→
STEP 4
Test-Time Compute
Search / reranking / self-consistency

1. You rarely need Step 3

Most teams stop at Step 2 and get most of the benefit.

2. Steps 3 & 4 are complementary

Training raises the ceiling. Test-time compute extracts it.

3. Steps aren't exclusive

2026 practice mixes them per capability.

What Production RL Actually Looks Like

In ads, ranking, and recommendation, the online-learning default has been a contextual bandit for a decade.

The Pattern

request ─► context ─► POLICY ─► guardrail ─► serve
                  │           │          │
                  │           │          ▼
                  ▼           ▼      user acts
             log decision  exposure
             + propensity    caps    OBSERVE OUTCOME
                                            │
                                            ▼
                                  UPDATE STATE (O(1))

The Economics

Policy state — ONE key-value read
Latency budget — fits inside one request
Update cost — O(1), milliseconds
Storage — ~500 numbers per user
Infrastructure — CPU, no GPU
Safety — reward floor, kill switch, canary

Track A updates weights in GPU-hours. Track B updates a few numbers in microseconds.
